# IT部知识共享服务平台 · 架构文档

> 版本：v1.4（2026-11-20，容量口径：约 1000 个注册读者、约 100 名内容维护者） · 配套文档：《需求文档.md》《原型图-界面.html》《效果图-新版/》（当前 UI 截图）

## 一、总体架构

```
                     公司内网（约 1000 个注册读者，约 100 名维护者）
┌────────────────────────────────────────────────────────────────────┐
│  浏览器（全员查阅 / 登录编辑：LDAP 域账号或本地账号）                    │
└──────────────────────────────┬─────────────────────────────────────┘
                               │ HTTP
┌──────────────────────────────▼─────────────────────────────────────┐
│  nginx（入口 80，单副本）                                             │
│  ├─ /      → Vue3 静态产物（gzip/br + hash 文件名 + 强缓存）            │
│  └─ /api/* → proxy_pass app:8080（单实例直连）                        │
├────────────────────────────────────────────────────────────────────┤
│  app × 1（Spring Boot 2.7.18 / Java 8）**单副本起步**                  │
│  it-docs 单模块（包内分层：controller / service / repository / common）          │
│  · JWT 会话，不依赖本地 session                                        │
│  · 文件本体落宿主机 ./data/files（local 存储；MinIO 仅多副本可选）          │
├──────────────┬─────────────────────────────────────────────────────┤
│ MySQL 8.0    │ 宿主机 ./data/files                                 │
│ 12 张表       │ 图片 / 附件 / 头像                                   │
│ binlog 备份   │ 与数据库一起纳入备份                                   │
└──────────────┴─────────────────────────────────────────────────────┘
        ▲                                  ▲
  公司 LDAP / AD 域控                 二期：钉钉机器人
```

核心变化一句话：**数据从"编译进静态页"改为"存 MySQL，前端实时拉取"**——多人编辑、实时生效、审计、备份全部由此解锁。

容量口径：**按约 1000 个注册读者、约 100 名内容维护者规划**。这不是 1000 人同时在线的承诺；一期继续使用单机 Compose，搜索与列表在数据库完成权限过滤和分页，并监控实际峰值、慢查询、连接池与文件目录容量。上线前用接近生产的数据量验证常用查询 P95 不超过 2 秒。

但仍保留三条约定：**应用无状态（JWT）、文件持久化并纳入备份、写操作留痕**——理由不是性能，而是「换机器、恢复备份时不用返工」。

> 当前部署拓扑：单机 compose（nginx + app×1 + mysql），上传文件落 `./data/files`；不需要 MinIO / Redis。要加 app 副本时，需先把文件存储切到 MinIO 等共享对象存储，见 3.6。

| 不能用（Java 9+）                     | Java 8 替代写法                                          |
| -------------------------------- | ---------------------------------------------------- |

## 三、容量与性能设计（千人注册规模）

### 3.1 容量口径（1000 注册读者，不等于 1000 并发）

| 指标 | 目标值 | 说明 |
|---|---|---|
| 注册读者 | **约 1000 人** | 以匿名公开查阅和登录受限内容访问为主 |
| 内容维护者 | **约 100 人** | 通过空间编辑权限与单篇读取名单控制内容操作 |
| 峰值同时在线 / QPS | 上线观察后确认 | 当前没有同时在线人数和请求峰值数据，不把注册人数当并发承诺 |
| 文档量 / 文件量 | 上线前按迁移盘点建立基线 | 正文、附件和版本持续增长，监控数据库与 `data/files` 容量 |
| 查询性能 | 列表和搜索 P95 ≤ 2 秒 | 用接近生产的数据量和预期峰值负载测量 |

> 一期保留单机 Compose，但容量是否足够必须依据真实并发、慢查询和资源监控验证，不预设“并发不会成为瓶颈”。

### 3.2 一期规模：先保持架构简单，再按观测扩容

不要按千人规模堆组件，但下面这些和"规模"无关、和"好不好用/以后会不会返工"有关，建议保留：

| 项 | 建议 | 理由（与规模无关） |
|---|---|---|
| **JWT 无状态会话** | 保留 | 不用 session 同步，换机器/加副本零改动；实现成本比 session 更低 |
| **文件持久化** | 保留 | 单机用宿主机目录 `./data/files`，容器重建不丢；备份脚本打包该目录；以后加副本再切 MinIO |
| **中文全文索引 ngram** | 保留 | 1000 篇 `LIKE '%词%'` 也能跑，但搜不准、越用越慢；建表时加索引零成本 |
| **后端分页 + 静态资源强缓存** | 保留 | 前端首屏体验，和并发无关 |
| **写操作 before/after 审计** | 保留 | 知识库的核心诉求之一（谁改的、改成什么），事后补不回来 |
| **连接池 / 慢查询巡检** | 保留（阈值放宽） | Hikari 默认 10 即可；慢查询 > 1s 仍视为缺陷 |

一期先不引入复杂组件，但以下扩容选择由数据触发：

| 不做 | 原因 |
|---|---|
| app 常驻多副本 / K8s | 单人维护，多副本只增加排障成本；local 文件存储也无法跨副本共享 |
| Redis / 读写分离 / 独立搜索集群 | 先用 MySQL + Caffeine；按慢查询、连接池等待及并发监控决定是否引入 |
| 深分页游标、异步导出任务 | 数据量小，`LIMIT` 分页足够；导出直接同步返回 |
| 无依据的高并发承诺 | 先确认实际峰值，再将容量目标固化为可重复的压测场景 |

### 3.3 索引与 SQL 约束（建表即建）

| 表 | 索引 | 用途 |
|---|---|---|
| `it_doc` | `uk_doc_no(doc_no)`、`idx_space(space_id, status, updated_at)`、`idx_status_time(status, updated_at)` | 唯一编号 / 空间列表 / 全站最新 |
| `it_doc` | `FULLTEXT ft_search(title, summary, content_md, tags) WITH PARSER ngram` | 中文全文检索（摘要/一句话答案也参与命中；默认分词器按空格切，中文搜不到，**必须 ngram**） |
| `it_doc_version` | `idx_doc_ver(doc_id, version_no)` | 版本列表与回滚 |
| `it_space_acl` | `idx_space_subject(space_id, subject_type, subject_name)` | 空间鉴权命中 |
| `it_doc_acl` | `uk_doc_subject(doc_id, subject_type, subject_name)`、`idx_subject_doc(subject_type, subject_name, doc_id)` | 单篇读取限制 |
| `it_file` | `idx_sha_doc_uploader(sha256, doc_id, uploaded_by)`、`idx_doc(doc_id)` | 同文档/上传人去重 / 按文档查附件 |
| `it_op_log` | `idx_time(op_time)`、`idx_doc(doc_id, op_time)`、`idx_op(operator, op_time)` | 日志筛选 |

硬约束：

- 列表接口**禁止无 limit 查询**（默认 20 / 上限 100）；导出直接同步返回即可，体量小。
- 正常 `LIMIT offset` 分页即可；单空间文档 > 2000 篇再考虑游标，现在不做。
- 连接池：单副本 Hikari `maximumPoolSize=10~20`（默认 10 够用），MySQL `max_connections` 保持默认 151 即可。
- 慢查询阈值 500 ms，超 1 s 视为缺陷；上线前 `EXPLAIN` 过一遍列表与搜索 SQL。
- `it_op_log` 超 12 个月转 `it_op_log_archive`（同结构）；按日志增长量和审计保留期执行归档。

### 3.4 缓存策略（Caffeine 为主，Redis 可选）

一期**默认只用 Caffeine 进程内缓存**，不装 Redis；满足以下任一条件再引入 Redis：① 常驻 app 副本 ≥ 2；② 要求停用/改权限**跨副本秒级生效**；③ 想给查阅端做统一限流。

| 缓存 | 方式 | TTL | 失效方式 |
|---|---|---|---|
| 空间 ACL 结果 | Caffeine | 5 min | 配置变更时主动 `invalidate` |
| 用户域组 | Caffeine | 10 min | 登录刷新；管理员「清缓存」按钮 |
| 用户状态 | Caffeine | 60 s | 停用时主动 `invalidate`（最多 60 s 生效） |
| 热点文档 / 首页统计 | Caffeine | 60 s | 更新/删除时 `invalidate` |

> 单副本时 Caffeine 失效是**同步即时**的，比 Redis 还准。加 Redis 后按 `acl:space:{id}` / `usr:{name}:status` 二级缓存，Caffeine 30 s → Redis → DB，Redis 挂了只打 WARN、照常回源。

> 域组变更的生效延迟：AD 加人后最长 10 分钟（缓存 TTL）生效；要求立即生效时点管理台「清缓存」，或在成员页对该用户重新拉取域组。

### 3.5 压测验收（按注册规模与实测峰值确认）

| 项 | 标准 |
|---|---|
| 场景 | 以生产数据量和上线观察到的峰值并发为基线，覆盖搜索、列表、详情、附件及编辑保存 |
| 工具 | k6（轻量，脚本随工程交付；不必上 JMeter 集群） |
| 通过线 | 列表和搜索 P95 ≤ 2 秒、错误率 < 0.1%；记录详情和编辑接口延迟基线 |
| 资源 | app CPU < 70%、内存无持续增长（无 OOM / 无泄漏） |
| 数据库 | 慢查询（>1 s）0 条、连接池等待 0 次 |
| 前端 | 首屏（内网千兆）< 1.5 s，重复访问（命中缓存）< 600 ms |

### 3.6 扩容路径（按监控指标触发）

| 阶段 | 拓扑 | 触发条件 |
|---|---|---|
| 一（起步，当前） | 单机 compose：nginx + app×1 + mysql；文件落 `./data/files` | 约 1000 个注册读者；先观察真实并发 |
| 二（备用） | 文件切 MinIO 等共享对象存储，app 加到 2 副本；nginx 动态解析 | 常驻副本 > 1 或需要发版不中断 |
| 三（后续评估） | MySQL 主从；必要时独立搜索 | 慢查询、数据库资源或搜索延迟持续超过目标 |

> 扩容依据是实际同时在线、接口延迟、连接池等待、慢查询和资源使用，不是单看账号数。

### 4.1 分层调用约定

`controller → service(接口) → repository(接口) → mapper → DB`，单向依赖，不允许反向也不允许跳层。

| 层 | 形态 | 允许做 | 禁止做 |
| --- | --- | --- | --- |
| `controller` | 9 个类 | 收参、`@Valid` 校验、调 Service、转 DTO、包 `Result` | 拼 SQL、写业务规则、直接碰 Entity 输出 |
| `service` | 11 个接口 + `impl` 11 个实现 | 业务规则、权限校验、事务边界、审计埋点 | 出现 `QueryWrapper` / `Mapper` / 表字段名 |
| `repository` | 11 个接口 + `impl` 11 个实现 | 数据访问、查询条件拼装、分页 | 业务判断、抛业务异常、写审计 |
| `mapper` | MyBatis-Plus 接口 | 复杂 SQL（FULLTEXT 等注解 SQL） | 被 Service 直接注入 |

约定要点：
- **接口在 `service`/`repository` 包，实现在 `impl` 子包**，Spring 只对实现类打 `@Service`/`@Repository`，上层一律按接口注入。
- **嵌套值对象挂在接口上**（`SysConfigService.LdapConfig`、`LdapService.LdapUser`），实现类只做搬运，外部引用不随实现变动。
- `@Transactional` 只出现在 `service.impl`；`repository` 层不加事务，避免自调用失效与事务粒度过碎。
- `QueryWrapper`、表名、列名只允许出现在 `repository.impl` 与 `mapper`，Service 传的是业务参数（如 `spaceId/system/category/docType/page/size`）。

### 4.2 注释约定（谁写文档、谁写说明）

同一句说明不写两遍：**对外可见的字段靠 `@Schema`，对内可见的字段靠 Javadoc**。

| 层 | 类级 | 字段 / 方法级 | 为什么不重复 |
| --- | --- | --- | --- |
| `repository.entity` | Javadoc：这张表干什么、和其他表什么关系 | 每个字段一行 Javadoc：业务含义 + 枚举取值 + 指向哪张表 | **不加 `@Schema`**。实体不出 Web 层（DTO 转换后才返回），加了不会进 Swagger，反而诱导后来者直接返回实体 |
| `dto` | Javadoc 一句话 + `@Schema(name, description)` | 字段 `@Schema(description, example)`，必填标 `requiredMode` | 说明写在 `@Schema`，Swagger UI 与 IDE 都能看，不再另写 Javadoc |
| `repository` / `service` 接口 | Javadoc：职责边界（允许做什么、不做什么） | 方法 Javadoc：语义、参数含义、抛什么异常、有无副作用 | 接口是契约，实现类写「怎么做的」 |
| `repository.impl` / `service.impl` | Javadoc：实现策略（委托谁、缓存策略、事务边界） | 私有方法写清楚前置条件 | — |
| `mapper` | Javadoc：映射哪张表、有没有手写 SQL | 自定义 SQL 必须写清过滤条件与排序 | — |

枚举取值统一收在 `common/Constants`，实体与 DTO 的注释里把取值列全（如 `ACTIVE 正常 / DELETED 逻辑删除`），避免读代码时反查。

要点：

- **空间可见性**：`it_space.visibility` 三档——`PUBLIC` 匿名可看（问题记录）、`INTERNAL` 登录可看（业务文档、技术文档）、`RESTRICTED` 仅授权名单。业务/技术文档的收紧由一次性迁移 `content_scope_v1` 完成，管理员之后可在「空间与权限」里调整。
- **个人区域**：`it_space.space_type=PERSONAL`，`owner` 直接记在空间行上；后端查询强制 `space.owner=current_user`，管理员不可越权读。
- **软删除**：`status=DELETED`，列表过滤，日志保留 before/after。
- **qa 结构化字段**放 `content_json`（MySQL JSON 列），避免 15 个碎列；筛选/统计用生成列或应用层聚合。
- **钉钉预留**：`it_doc` 与 `it_space` 的 `source_type/source_id`、`it_group_bind` 一期建表即建，二期只写代码。

### 5.1 文件表 `it_file` 设计（统一一张表）

**原则**：文件元数据全部进 `it_file`，**文件本体落持久化目录**，文档正文只存引用，不存二进制。当前单机部署用 local 存储：容器内 `/app/data/files` 挂到宿主机 `./data/files`，容器重建不丢；备份脚本把该目录和数据库一起打包。

> `itdocs.storage.type=minio` 是可选实现，仅在需要多副本共享文件时启用（需自备 MinIO/S3）；单机部署不必安装。

| 字段                            | 说明                                                        |
| ----------------------------- | --------------------------------------------------------- |
| `id`                          | 主键                                                        |
| `biz_type`                    | `IMAGE` 图片 / `ATTACHMENT` 附件 / `AVATAR` 头像（后续扩展只加枚举值）     |
| `origin_name`                 | 原始文件名（下载时还原，如「WMS接口部署手册.docx」）                            |
| `stored_name`                 | 对象键名 = `<sha256前16>.<ext>`，防重名、防中文名乱码                    |
| `rel_path`                    | 对象键前缀 `files/2026/11/ab/cd/<stored_name>`，按年月分目录，避免单前缀对象过多 |
| `ext` / `mime` / `size_bytes` | 类型与大小；上传按白名单校验（图片 png/jpg/webp，附件 docx/xlsx/pdf/zip 等）    |
| `sha256`                      | 内容哈希，**同哈希复用同一条记录**（重复上传不重复占盘）                            |
| `doc_id`                      | 归属文档（可空：先上传后引用；文档删除时软标记，不物理删文件）                           |
| `uploaded_by` / `created_at`  | 上传人与时间，审计可查                                               |


**业务规则**：

1. 上传接口返回 `{ id, url }`，正文里存 `url`（如 `/api/files/1024/view`），**不存物理路径**——换存储方案不影响已存内容。
2. 图片在正文里渲染为 Markdown 图片；附件渲染为下载链接（带原始文件名与大小）。
3. 删除文档只标记文件为「待清理」，由定时任务清理无引用的孤儿文件（避免误删他处引用）。
4. 单文件上限 20 MB（可配）；图片上传后服务端做尺寸压缩与 EXIF 清理。

### 5.2 用户与认证（LDAP + 本地账号双通道）

用户统一存 `it_user`，用 `auth_source` 区分认证方式，**不为两种账号建两张表**。

| auth_source | 密码 | 来源 | 典型用途 |
|---|---|---|---|
| `LDAP` | 不存（`password_hash` 为空） | 域账号，首次登录自动建档 | 公司正式员工 |
| `LOCAL` | BCrypt 哈希（strength 10） | ADMIN 在「成员角色」页手动创建 | 外包/无域账号同事、钉钉机器人 service 账号、应急管理员账号 |

**登录判定顺序**（`authSource` 缺省时自动识别）：

```
1. 按 username 查 it_user
   ├─ 命中且 auth_source=LOCAL → BCrypt 校验 password_hash
   ├─ 命中且 auth_source=LDAP  → 走 LDAP bind
   └─ 未命中                  → 走 LDAP bind，成功后自动建档（LDAP 用户免注册）
2. LDAP bind 失败且库中存在同名 LOCAL 账号 → 拒绝，提示"该账号为本地账号，请用本地密码登录"
3. 校验通过 → 检查 status=ACTIVE → 签发 JWT（含 userId/username/role/域组列表）
```

**规则**：

1. LDAP 用户**自动开通**，默认角色 `VIEWER`，`display_name`/`email` 从域同步；ADMIN 只需提权，不用逐个建号。
2. 本地账号由 ADMIN 创建：用户名不得与已有域账号重名（防混淆），创建时校验冲突并提示。
3. 本地账号密码规则：≥8 位含字母数字；ADMIN 重置后生成临时密码，标记 `must_change_pwd`，首次登录强制改密。
4. 停用（`status=DISABLED`）即时生效：每次请求校验用户状态，JWT 未过期也拒绝。
5. **域组权限只对 LDAP 用户生效**；本地账号的空间权限只能通过 ACL 直授（`subject_type=USER`）。
6. LDAP 服务不可用时降级策略可配：`auth.ldap.fail-open=false`（默认）——仅本地账号可登录，域账号提示稍后重试；应急管理员用本地账号进系统。
7. 登录成功更新 `last_login_at`；本系统只面向内网账号，不做失败计数与账号锁定，避免域控故障或误操作把人锁在门外。

## 六、API 设计（REST，/api 前缀）

设计原则：**资源用名词复数、动作用 HTTP 方法、子资源挂在父资源下、批量/局部更新用 PATCH**。
不再出现 `/users/{id}/role`、`/spaces/all`、`/ldap-config` 这类「动词式 URL + 独立单例资源」。

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/auth/login` | 公开 | 双通道认证（本地 BCrypt / LDAP bind，首登自动建档）→ 发 JWT |
| GET | `/api/users/me` | 登录 | 当前用户 + 个人区域 + 公共空间列表（原 `/auth/me`） |
| PUT | `/api/users/me/password` | 登录 | 本人改密（原 `/auth/change-password`） |
| GET | `/api/users?keyword&authSource&page&size` | ADMIN | 成员分页（返回 `UserDTO`，无 passwordHash） |
| POST | `/api/users` | ADMIN | 创建本地账号，响应带一次性临时密码 |
| PATCH | `/api/users/{id}` | ADMIN | 局部更新 role / status / displayName / email（原 `PUT /{id}/role`、`PUT /{id}/status`） |
| PUT | `/api/users/{id}/password` | ADMIN | 重置密码，返回 `{message: 临时密码}`（原 `PUT /{id}/reset-password`） |
| GET | `/api/docs?spaceId&system&category&docType&keyword&page&size` | 公开 | 查阅端列表，返回 `DocDTO`（不含正文）；匿名只返回 `visibility=PUBLIC` 空间（问题记录） |
| GET | `/api/docs/{id}` | 公开 / 登录 | 详情，返回 `DocDetailDTO`（含正文）；`INTERNAL` 空间要登录，个人区域校验归属 |
| POST | `/api/docs` | 登录 | 新建；Service 判定空间写权限 |
| PUT | `/api/docs/{id}` | 登录 | 全量更新（写版本快照 + 审计） |
| DELETE | `/api/docs/{id}` | 登录 | 软删除 |
| PUT | `/api/docs/{id}/space` | 登录 | 换空间：个人区域 → 公共空间即「发布」（原 `POST /{id}/publish`） |
| GET | `/api/docs/{id}/versions` | 按文档读权限 | 版本列表 |
| POST | `/api/docs/{id}/versions/{no}/restore` | 登录 | 回滚到指定版本 |
| POST | `/api/files` | 登录 | 上传（multipart + bizType/docId），返回 `FileDTO{id,url,name,size}` |
| GET | `/api/files/{id}/view` | 公开 | 图片内联预览（sha256 内容寻址，一年强缓存） |
| GET | `/api/files/{id}/download` | 公开 | 附件按原名下载 |
| DELETE | `/api/files/{id}` | 登录 | 逻辑解绑，孤儿由定时任务清理 |
| GET | `/api/spaces?scope=public\|all` | public 公开 / all ADMIN | 空间列表（原 `GET /spaces/all`） |
| POST | `/api/spaces` | ADMIN | 新建公共空间 |
| PUT | `/api/spaces/{id}` | ADMIN | 改名 / 改描述（编码不可改） |
| GET | `/api/spaces/{id}/acl` | ADMIN | 授权列表 |
| PUT | `/api/spaces/{id}/acl` | ADMIN | 全量覆盖授权（提交数组） |
| GET | `/api/op-logs?docId&operator&page&size` | ADMIN | 操作日志分页 |
| GET | `/api/settings/ldap` | ADMIN | 读 LDAP 配置（原 `/api/ldap-config`） |
| PUT | `/api/settings/ldap` | ADMIN | 保存即生效，无需重启 |
| POST | `/api/settings/ldap/test` | ADMIN | 测试连接（填账号走真实 bind，否则探测连通性） |
| POST | `/api/import/zip`、`/api/import/docx` | ADMIN | 批量导入（P1，未实现） |

统一约定：

- 返回体 `{code, msg, data}`；分页统一 `{total, page, size, list}`（不把 MyBatis-Plus 的 `Page` 直接吐给前端）。
- 错误只走一条路：Service 抛 `BizException` → `@RestControllerAdvice` 转 HTTP 状态 + `{code,msg}`；Controller 不写 `return Result.fail(...)`。
- 参数校验在 DTO 上（`@NotBlank/@Size/@Pattern/@Email`），Controller 加 `@Valid`，失败统一 400 + 首条字段提示。
- 分页参数基类 `PageQuery`：默认 20、上限 100，越界静默纠正。
- 写操作全部记 `it_op_log`（before/after JSON）。

### 6.1 接口文档（springfox / Swagger UI）

后端集成 springfox 3.0.0（Swagger 2 规范；Boot 2.6+ 需 `ant_path_matcher`，见 `Swagger2Config`），启动即可在线查看调试：

| 入口 | 地址 | 用途 |
|---|---|---|
| Swagger UI | `/swagger-ui.html` | 在线调试；右上 Authorize 粘贴登录 token（Bearer），可调全部接口 |
| Swagger 2 JSON | `/v2/api-docs` | 导入 Apifox / Postman |

实现约定（全部 Controller 覆盖）：

- Controller 用 `@Api(tags = "01. 认证")` 分组（序号前缀保证排序），方法用 `@ApiOperation(value, notes)` 写行为说明与失败码。
- 请求 / 响应 DTO 用 `@ApiModel` / `@ApiModelProperty`（描述 + example）；实体不出 Web 层，Swagger 里只有 DTO。
- 公开接口（登录 / 文档列表详情 / 空间列表 / 附件预览下载）无需 token，其余接口需在 Authorize 里填 `Bearer <token>`。
- 生产不对外暴露：compose 里 app 只 `expose: 8080`，nginx 只反代 `/api`；在线调试时临时映射端口访问，用完改回（见部署手册验证清单第 5 条）。

## 七、权限校验链路

分三层，各管一段，不重复也不遗漏：

```
① 认证（JwtInterceptor）
   白名单（方法:路径，* 单段 / ** 多段，其余完全匹配）→ 放行；带 token 则尽力绑定身份
     如 GET:/api/docs/**、GET:/api/files/*/view
     注意不能写成 GET:/api/files —— 前缀匹配会连带放行 download
   其余请求 → 解析 JWT → 校验 it_user.status=ACTIVE → 挂 AuthContext(ThreadLocal)

② 角色（@RequireRole 注解，拦截器统一判定）
   方法上的注解优先于类上；角色不符 403，未登录 401
   例：UserController 成员管理标 ADMIN；/me 标三种角色；SettingsController 整类 ADMIN

③ 资源（Service 层）
   读公共空间：visibility=PUBLIC 放行（含未登录）；INTERNAL 需登录；RESTRICTED 查名单
   读个人区域：owner==currentUser（ADMIN 也不越权；currentUser 为 null 直接 403）
   写公共空间：全局角色 ≥EDITOR 且 it_space_acl 命中 EDITOR（USER 直授 / 二期 LDAP 域组）
   写个人区域：仅 owner

   数据权限（按业务系统，DocService#scopeOf）：it_user.sys_scope 空 = 不限；
   非空 = 只出「归属这些系统的文档 + 无系统归属的文档」，repository 层拼 biz_system IN。
   读越权按「不存在」返回（不暴露存在性），写越权 403；新建与更新都不允许把 system
   设成范围外值；个人区域草稿不受此约束；ADMIN 与未登录不叠加此层。

   两处「公开路径必须补二次鉴权」的地方：
   · 文件 view/download：匿名可访问，但文件挂在文档下时按该文档的读权限判定（FileService#mustReadable）
   · 文档列表/搜索：不传 spaceId 时收敛为「公共空间 + 本人个人区域」，repository 层拼 IN，不让个人区草稿进结果集
```

> 以前每个 Controller 各写一份 `requireAdmin()`，加个接口就得记得补一次；现在权限写在注解上，漏标就是「默认要登录」，不会漏判。

- **域组命中**：仅 `auth_source=LDAP` 的用户有域组。ACL 判定时用配置的 LDAP 查询账号 bind，按 `sAMAccountName` 查 AD 的 `memberOf`（Caffeine 缓存 5 分钟），再与 `subject_type=LDAP_GROUP` 的 `subject_name` 比对；组 `CN` 或完整 `DN` 均可命中，不含嵌套组。未配置查询账号或 LDAP 不可用时按不命中处理（fail-closed），用户直授不受影响。
- **本地账号**：没有域组，只能靠 `subject_type=USER` 的 ACL 直授；同样受空间级权限约束。
- **停用即时生效**：JWT 里带 `userId`，每次请求校验用户状态（Caffeine 60s → 回源 DB，单副本下停用时主动 `invalidate` 即时生效；若启用 Redis 再加一层 60s）。

## 八、部署与运维

```yaml
# docker-compose.yml 关键结构（当前拓扑：app 单实例，容量以实测为准）
services:
  mysql:    image: mysql:8.0
            卷 ./data/mysql；binlog 开启（log-bin + binlog_expire_days=7）
            初始化 /docker-entrypoint-initdb.d/init.sql（12 张表 + 索引 + 全文索引）
            healthcheck 走 TCP 并查 it_docs.it_space，避开 init 临时实例误判
  app:      build it-docs.Dockerfile，depends_on mysql（service_healthy）
            单实例常驻（`restart: unless-stopped`）；镜像 tag `itdocs-app:<tag>`
            卷 ./data/files:/app/data/files；storage.type=local
            环境变量：DB / JWT / LDAP；healthcheck /actuator/health
  web:      build it-docs-web.Dockerfile；镜像 tag `itdocs-web:<tag>`；80 端口
            /api → app:8080（nginx 用 Docker DNS + 变量 proxy_pass 动态解析）
            健康检查直通 app /actuator/health
volumes: 全部 bind mount 到宿主机 ./data/（备份=直接拷目录）
```

> 当前拓扑**不支持 `--scale app=2`**：两个 app 容器看不到彼此的本地 `data/files`。要扩到多副本，先把 `storage.type` 切到 MinIO 等共享对象存储，再加副本和负载均衡。nginx 已配置动态解析，app 容器重建不会因缓存旧 IP 而 502。

| 事项   | 方案                                                         |
| ---- | ---------------------------------------------------------- |
| 发版   | `bash scripts/backup.sh` → 给当前镜像打 `backup-日期` tag → `docker compose build app web` → `up -d`（约 15~30 秒中断，建议下班后发）。数据在 `./data/`，容器可随时重建 |

| 容量巡检 | 每月看：表大小、慢查询 TOP10、`it_file` 孤儿数、日志表行数（>12 个月归档）、`data/files` 与备份盘余量 |
